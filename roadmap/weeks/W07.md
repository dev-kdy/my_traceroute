# W07 — ICMP 오류 안의 원본 패킷과 Probe 식별

**선수조건:** W04 안전한 파서, W05 송신, W06 ICMP 수신. 이번 주 핵심은 **ICMP가 왔다는 것만으로 내 요청의 응답임을 확정할 수 없다**는 점이다.

**주간 산출물:** `Probe`(식별할 수 있는 전송 시도), `ObservedIcmp`(해석된 수신), `MatchResult`(일치/불일치/불충분) 모델과 결정적 테스트. **실험 중 다른 Probe를 내 것으로 오인하면 불합격**.

## 1차시 — ICMP Error Payload/Quoted Packet

### 네트워크 기초

- ICMP Time Exceeded/Port Unreachable 바디에는 **해당 오류를 촉발한 원래 IP 패킷의 일부**가 인용된다. 이 정보를 사용해 사용자 프로세스의 어떤 Probe인지 연결한다.
- Outer IPv4 header → ICMP error header → Quoted inner IPv4 header → 인용된 UDP/ICMP 전송계층. **각각 길이가 서로 다를 수 있다.**
- Outer/inner IHL이 모두 20바이트라고 가정하지 않는다. 실제 수신 `nbytes`와 IP Total Length를 확인.
- UDP source port/destination port, IP src/dst, IP Protocol, ICMP Echo ID/Sequence를 어느 위치에서 읽을지 종이에 계산.
- 일부 라우터/중간 장치가 인용하는 바이트 수는 다를 수 있으므로 **불충분한 정보**를 매칭 성공으로 만들지 않는다.

### Rust 문법

- `struct Probe` 또는 기록 타입: TTL, 목적지, 포트/ID, probe sequence, 송신 시각 등 필요한 값. 단순 숫자 하나로 전체 요청을 대표하지 않는다.
- `enum`/`match`로 `Matched/Unrelated/Malformed` 등을 모델링. Java sealed class/enum과 비슷한 점과 Rust의 타입 유효성을 비교.
- `&[u8]`의 안전한 하위 slice, `Option/Result`의 실패 상태 구분.

### C 원본 전체 독해

[`check_packet.c`](https://github.com/Dauie/traceroute/blob/master/src/check_packet.c): `icmppkt_check`/`udppkt_check`에서 `IPV4_HDRLEN + ICMP_HDRLEN + IPV4_HDRLEN` 위치로 이동해 식별 필드를 읽고, `check_packet`이 모드에 따라 분기하는 전체 흐름. 원본 UDP는 `pid+ttl`/고정 base port로 검사하므로 같은 홉 내 여러 Probe를 충분히 식별하는지 의심하고 **테스트로 판단**.

### 단계별 실습

1. 서로 구별해야 할 **3개의 Probe**(같은 TTL에서 순번만 다른 경우 포함)를 설계.
2. 각 Probe마다 인용된 UDP 헤더에서 확인 가능한 **고유 식별 규칙**을 정하고 C 방식과 비교.
3. 수신 버퍼의 outer IPv4/ICMP/inner IPv4/UDP 오프셋을 **실제 길이·IHL에서 계산**하는 파서 설계.
4. 안전하게 읽힌 필드가 현재 Probe와 같을 때만 `Matched` 반환하도록 구현.
5. 다른 source/destination port, IP, Protocol, 과거 TTL, 길이 부족을 모두 별도 테스트.
6. 의심되는 답이 오면 로그에 이유를 남기되 RTT나 도달 메시지를 출력하지 않는다.

### 테스트 데이터

| 상황 | 기대 |
|---|---|
| 정확한 IP/포트/ID가 일치한 quoted UDP | 일치 |
| source port만 다른 과거 Probe | 무관 |
| destination port만 다른 Probe | 무관 |
| inner IPv4 IHL=6, outer IHL=5 | 동적 오프셋 사용 |
| quoted UDP 헤더가 8바이트 미만 | 불충분/잘린 패킷 |
| outer 수신 길이가 헤더보다 작음 | 안전하게 거부 |

## 2차시 — 늦은·중복·무관한 응답의 함정

### 개념

- 여러 Probe가 전송되고 나중에 같은 TTL의 응답이 도착할 수 있다. 단순 홉 번호/라우터 IP로만 매칭하면 **오답 RTT**가 생김.
- NAT는 포트를 변경할 수 있고 ECMP는 Probe 필드에 따라 경로를 바꿀 수 있어 **단순한 추측 매칭**이 위험.
- ICMP Error Type/Code와 quoted 원본 패킷이 일치해야 의미 있는 관측으로 처리 가능.
- '내가 보냈는가?'와 '목적지에 도착했는가?'는 독립된 검사.

### C 원본 분석

[`handle_response.c`](https://github.com/Dauie/traceroute/blob/master/src/handle_response.c)의 `handle_response`가 먼저 `check_packet`을 호출한 뒤 주소/RTT를 출력하는 흐름, `ping_loop`의 마지막 버퍼 IP만 비교하는 종료 분기를 같이 읽는다. **한 번의 매칭 실패가 어떤 출력과 종료 동작으로 이어지는가**를 추적.

### 구현 순서

1. `ProbeId` 생성 규칙을 **동일/다른 홉**에서 충돌하지 않도록 설계.
2. 보낸 Probe와 수신 Candidate를 연결하는 함수의 입력/출력 타입 설계.
3. 무관한 응답은 건너뛰고 deadline 내에서 다음 응답을 기다릴 수 있도록 **상태** 정의(실제 시계는 W08).
4. 지난 Probe의 늦은 ICMP를 현재 Probe로 오인하지 않는 테스트.
5. 동일 ICMP가 두 번 들어와도 RTT를 중복 출력하지 않는 테스트.
6. W05~06의 수신 코드와 순수 매칭 함수를 분리하여 관리자 권한 없는 `cargo test` 실행.
