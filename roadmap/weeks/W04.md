# W04 — 네트워크 패킷 바이트와 안전한 파싱

**선수조건:** W03 M1, `Result`, 기본 모듈/타입. 이번 주는 **외부 네트워크나 관리자 권한 없이** 바이트 배열/fixture로 IPv4·UDP·ICMP를 파싱한다.

**핵심 철학:** 패킷을 읽기 전에 길이를 검증한다. 안전한 파서와 소켓 코드를 분리해 **오프라인 테스트**가 가능해야 한다.

## 1차시 — Byte/Slice/Endianness/Bit 연산

### 개념

- `u8` 1바이트, `[u8; N]` 고정 배열, `Vec<u8>` 동적 버퍼, `&[u8]` 빌린 바이트 뷰. Java `byte[]`는 signed byte라 변환 시 주의.
- `slice.get(range)`가 `Option`을 반환하므로 인덱스 초과를 안전하게 처리할 수 있다. 무조건 `buffer[20]`에 접근하지 않는다.
- Network Byte Order(Big-endian), `u16::from_be_bytes`, `to_be_bytes`; Java `ByteBuffer.order`와 비교.
- 비트마스크/Shift/`&`/`|`: IPv4 첫 바이트에서 Version(상위 4비트)과 IHL(하위 4비트)을 분리하는 방식.
- **IPv4 IHL × 4바이트**가 실제 IP 헤더 크기; 최소 20바이트지만 옵션 있으면 더 길다.
- 총 길이·UDP Length·IP Protocol 값과 실제 buffer length가 일치하는지 별도 검사.

### C 원본 전체 함수 읽기

[`traceroute.c`](https://github.com/Dauie/traceroute/blob/master/src/traceroute.c)의 `fill_packet`: `ft_memcpy`로 IPv4/UDP/ICMP 헤더, 타임스탬프, 데이터를 순서대로 buffer에 놓는다. 실제 헤더 길이 상수를 어떻게 적용하는지 추적. C cast를 Rust slice 인덱싱으로 무조건 번역해서는 안 됨.

### 직접 구현하는 과제

1. **파서 API 계약**을 먼저 정의: 입력 `&[u8]`, 성공 결과의 필드, 실패 종류. 반환 `Result` 선택 이유 설명.
2. 첫 바이트에서 IPv4 Version/IHL 계산을 학습자가 직접 작성.
3. 최소 IPv4 헤더/가변 IHL/실제 버퍼 길이/Total Length를 검증.
4. `Protocol=1` 또는 `17`에 따라 UDP/ICMP 시작 오프셋 계산.
5. 바이트 순서가 바뀐 포트/길이를 디버깅하도록 2바이트 테스트 값으로 직접 계산.
6. 모든 기능을 별도 작은 함수로 작성하고 `cargo test`로 확인.

**미리 준비할 테스트 데이터:** 길이 0, 1, 19, 20, 24; Version 6, IHL 4, IHL 5/6; 총 길이 < 헤더 길이, 총 길이 > 실제 수신 길이. 예상 성공/실패를 코드 전에 표로 기재.

## 2차시 — IPv4/UDP/ICMP 헤더와 체크섬

### 프로토콜 표준 구분

- [RFC 791](https://www.rfc-editor.org/rfc/rfc791): Version/IHL/Total Length/Identification/Flags+Offset/TTL/Protocol/Header Checksum/Source/Destination. IPv4 헤더 checksum은 **헤더용**, 페이로드 데이터 전체 검사가 아니다.
- [RFC 768](https://www.rfc-editor.org/rfc/rfc768): UDP Source Port/Destination Port/Length/Checksum, IPv4 pseudo-header 포함 체크섬 개념. IPv4 UDP 체크섬의 0 처리 등 예외를 문서로 확인.
- [RFC 792](https://www.rfc-editor.org/rfc/rfc792): ICMP Type/Code/Checksum 및 Time Exceeded·Destination Unreachable의 quoted packet. 실제 오류 메시지 길이는 충분할 수도 부족할 수도 있다.

### C 원본 분석

[`check_packet.c`](https://github.com/Dauie/traceroute/blob/master/src/check_packet.c)의 `icmppkt_check`/`udppkt_check`/`check_packet` 전체: `IPV4_HDRLEN + ICMP_HDRLEN + IPV4_HDRLEN` 고정 오프셋 후 포트/ID를 읽는다. 이것이 **항상 안전하다는 증거는 없다**. outer/inner IHL이 다른 테스트 데이터를 만들어 판단한다. [`traceroute.h`](https://github.com/Dauie/traceroute/blob/master/incl/traceroute.h)에서 사용한 기본값/구조를 확인하되 Rust에서 C 구조체 메모리를 그대로 transmute하지 않는다.

### 단계별 구현

1. 캡처 데이터가 없어도 가능한 **순수 함수** `parse_ipv4`의 입력·오류 계약 설계.
2. 동적 IHL 기반 IP 이후 프로토콜 헤더 위치 계산.
3. `parse_udp`와 `parse_icmp`의 최소 길이 검사·필드 읽기.
4. 체크섬 계산의 대상 범위·홀수 길이 처리·overflow folding을 종이에 계산(완성 코드 대신 예제 값 사용).
5. 정상·잘린·변조 테스트 추가, 실패하면 `Err` 반환하고 panic 발생 금지.
6. 원본 C의 고정 오프셋 가정과 새 파서 설계 차이를 **실제 테스트**로 설명.

### 필수 검사 매트릭스

| 사례 | 요구 |
|---|---|
| IPv4 20바이트, Version 4, IHL 5 | 기본 파싱 |
| IPv4 옵션 포함, IHL 6(24바이트) | 다음 헤더 시작 위치 4바이트 이동 |
| 수신 buffer 19바이트 | 길이 오류, panic 없음 |
| Total Length < IHL×4 또는 > 제공 바이트 | 길이 불일치 검증 |
| UDP 헤더 8바이트 미만 | 잘린 UDP 거부 |
| ICMP 8바이트 미만 / quoted 데이터 부족 | 부분 정보 처리/오류를 명확히 구분 |
| Big-endian 포트 33434 | 정확한 숫자 변환 |
| 체크섬 불일치 | 해당 검증 정책에 따라 거부/구분(실험과 OS offload 고려) |

## Exit Gate

- [ ] IHL·Total Length·Protocol·포트/Type/Code를 바이트 단위로 설명.
- [ ] 패킷 파서가 **소켓 없이** 테스트되며 잘린 버퍼에 panic 없음.
- [ ] `from_be_bytes` 등 바이트 순서 사용 이유를 설명.
- [ ] C `fill_packet`/`check_packet` 전체 흐름과 위험 가설 구분.
- [ ] 정상·경계·오류 테스트·`fmt/clippy/test` 증거 제출.
