# W02 — Ownership·Borrowing과 상태 구조체

**선수조건:** W01 통과. TTL/Probe 시뮬레이터와 C `t_mgr`의 필드 역할을 설명할 수 있어야 한다. W02에서는 패킷 송신을 새로 구현하지 않는다.

**주간 결과:** `Config`(설정 타입), `ProbeProtocol`(모드), 기본값·유효성 검증 테스트, C `t_mgr`와 Rust 상태 모델 차이 설명.

## 1차시 — 메모리 모델과 Ownership

### 개념(공식 Rust Book Ch 4)

- Stack vs Heap: 지역 값 저장과 동적 데이터 버퍼의 차이, 타입별 실제 데이터 위치를 추측하지 말고 `String`의 소유한 버퍼 사례로 이해.
- Ownership: 각 값의 소유자, scope 종료와 `Drop`, move와 copy 구분.
- `String` vs `&str`: 소유 UTF-8 버퍼와 문자열 뷰. Java String은 'Rust String과 동일'이라는 비유 금지.
- Borrowing: `&T`/`&mut T`의 규칙, 데이터 경쟁 방지 목적, 가변 참조 독점. 컴파일 오류를 일부러 만나보고 해석.
- Java GC는 Rust의 소유권·라이프타임 검사와 같지 않다. Rust는 일반적인 추적 GC 없이 자원을 관리한다.

### C 읽기(전체 함수 지도)

[`main.c`](https://github.com/Dauie/traceroute/blob/master/src/main.c)의 `main()`: `t_mgr *mgr` 할당, 기본값 설정, 파싱, 사용, `free`. 함수 전체를 읽고 **누가 관리자 메모리를 소유하고 해제하는지** 표시. [`traceroute.c`](https://github.com/Dauie/traceroute/blob/master/src/traceroute.c)의 `traceroute()`에서 `msg.data`를 얻고 해제하는 지점을 표시. 외부 라이브러리 `ft_memalloc/ft_strdup` 구현 내부까지 아는 것으로 주장하지 않는다.

### 단계별 실습(정답 코드 금지)

1. `String`을 함수에 인자로 넘기는 두 설계(소유권 이전 / 읽기 빌림)를 스스로 예측.
2. 의도적으로 move 후 원래 변수를 출력해 컴파일 오류를 확인하고 이유를 설명.
3. `clone()`으로 무조건 해결하지 말고 읽기만 필요하면 어떤 참조가 적합한지 선택.
4. 동일 데이터를 읽는 두 공유 참조와 하나의 가변 참조가 언제 공존하지 못하는지 실험.
5. 기존 W01의 `domain` 출력 함수를 borrow를 사용해 고치되 함수 전체 정답은 튜터가 먼저 제공하지 않음.

**테스트·증거:** 실패하는 최소 Rust 코드/Compiler diagnostic/스스로 고친 diff/`cargo check` 종료 코드. 컴파일이 막힌 사례도 '학습 증거'로 기록.

## 2차시 — C `t_mgr`와 Rust `struct Config`

### 개념

- `struct` 필드와 생성, `impl` 메서드, `Default`; Java Class/record와 유사점이 있지만 메모리 모델/필드 불변성 차이.
- `enum ProbeProtocol`: 숫자/불린 플래그 조합보다 **유효한 경우만 표현**하려는 설계. `flags.icmp`과 `flags.udp`가 동시에 켜지는 상태를 어떻게 제한할지 설명.
- `u8` TTL(IPv4 헤더 필드는 8비트), `u16` 포트, `usize` 버퍼 길이, `bool` 모드/플래그 선택. C 헤더의 `int` 타입을 그대로 옮기지 않는다.
- 기본값·설정 검증: `first_ttl >= 1`, `first_ttl <= max_ttl`, UDP 포트 범위, Probe 수의 상한을 왜 두는지 설명.

### C 코드 전체 읽기

[`traceroute.h`](https://github.com/Dauie/traceroute/blob/master/incl/traceroute.h)의 `t_flags`, `t_mgr`, `DEF_INIT_TTL=1`, `DEF_MAX_TTL=30`, `DEF_PROB_AMT=3`, `DEF_UDP_PORT=33434`를 표시하고 필드가 실제로 어느 함수에서 바뀌는지 추적. `set_program_defaults()`를 다시 확인하며 '기본값 설정 → CLI 오버라이드 → 검증'이 Rust에서는 어떤 단계가 적절한지 설계한다.

### 직접 구현 순서

1. `Config`에 필요한 필드를 **먼저 표**로 설계하고 이유를 쓴다.
2. `ProbeProtocol`의 유효 상태를 설명하고 도메인 모델을 정의.
3. 기본값을 반환하는 방법을 선택(`Default` 또는 생성 함수)하고 테스트.
4. 범위를 벗어나는 TTL/포트/Probe 수를 어떻게 표현할지 결정.
5. W01의 TTL 시뮬레이터가 새 `Config`를 받아 출력하게 변경.
6. 원본 C 상태와 설계 차이를 5문장으로 정리(ownership, 값 유효성, 플래그, 오류, 자원 해제).

**실습 결과:** 소켓 없음. 테스트는 기본 설정, 시작>최대 TTL, Probe 0·상한 초과, 모드 유효성. 오류 타입의 세부 `Result` 설계는 W03에서 심화.

## 패킷/네트워크 연결과 검증

'Rust 문자열을 함수에 빌려주었다'는 것과 '네트워크 패킷을 전송했다'는 것은 전혀 다르다. 지난 W01의 TTL 그림을 사용해 `Config.ttl`이 향후 IPv4 `ip.ttl`로 직렬화될 지점을 **설계도에만** 표시. 추후 실제 송신은 W05.
