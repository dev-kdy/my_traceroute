# W01 — traceroute 네트워크 기초와 Rust 입문

> **현재 진행 중 / 완료 미확정.** 로컬에서 TTL 시뮬레이터의 기대 출력과 Clippy 완료 로그를 제출했으나, `cargo fmt --check` 종료 코드와 실제/대체 패킷 관찰, 전체 함수 흐름, 주차 평가가 남았다. [정확한 진도](../01-progress.md).

**학습 전제:** Java 경험 있음, Rust 첫 학습. macOS Apple Silicon, 사용자 보고 rustc/Cargo 1.100.0. 로컬 `Cargo.toml` Edition 미확인. 소켓 작성 **금지**; 기존 `main.rs`에서 단계적으로 개선.

**성과물:** (1) 주차 통합 TTL/Probe CLI 시뮬레이터 (2) C 전체 호출/TTL 흐름도 (3) Cargo 검사 로그 (4) 승인된 시스템 traceroute 또는 통제 대체 패킷 필드표 (5) 독립 구두 설명/오답 노트.

## 1차시 — IPv4·라우터·홉·TTL·ICMP 및 C 반복

### A. 학습 목표(설명할 수 있어야 함)

- IP 주소와 도메인 이름, Packet과 Probe, Router와 Hop의 차이.
- TTL이 **송신 프로그램에서 단계적으로 증가**하고 **경유 라우터에서 감소**하는 서로 다른 역할.
- TTL 만료에 대한 ICMP Time Exceeded(11/0), UDP 목적지 포트 미사용에 대한 Destination Unreachable/Port Unreachable(3/3)을 구분.
- RTT가 왕복 시간이라는 점과 `*`가 '기한 내 적절한 응답을 못 봄'이라는 점.
- traceroute가 경로 전체를 완벽하게 보장하지 않는 이유(제한, 방화벽, 비대칭, ECMP).

### B. 공식 원리와 예측 실험

**[RFC 791 / RFC 1812]** IP 패킷이 각 라우터를 통과하면서 TTL이 감소한다. 전달 중 TTL이 소진되어 폐기되면 일반적인 IPv4 홉 추적에서 ICMP Time Exceeded Type 11 Code 0 응답을 기대한다. 다만 답변이 제한되거나 필터링되어 실제로 보이지 않을 수 있다. **[RFC 792]** UDP 포트에 리스너가 없는 최종 목적지의 ICMP Type 3 Code 3을 UDP 방식의 도달 신호로 해석할 수 있으나 **응답이 내 Probe인지를 먼저 확인**해야 한다.

학습자가 먼저 종이에 예상하기: TTL=1/2/3을 각각 전송할 때, 첫 번째/두 번째 라우터에서 TTL 값이 어떻게 변하는가? TTL 1을 두 번째 홉에 도달한다고 상상하면 무엇이 잘못인가?

### C. 원본 C 전체 제어 흐름(단순 TTL 줄만 보지 말기)

[원본 `main.c`](https://github.com/Dauie/traceroute/blob/master/src/main.c): `main → set_program_defaults → parse_args → create_sock → traceroute`. 실패 분기/목적지 필수 검사를 포함하여 그린다.

[원본 `traceroute.c`](https://github.com/Dauie/traceroute/blob/master/src/traceroute.c): `traceroute → initialize_echopacket → update_echopkt → ping_loop`.

`ping_loop`의 **모든 단계**:
1. `run`, `ttl <= max_ttl` 확인.
2. `probe=0` 초기화, TTL 출력.
3. `while(probe++ < nprobes)`: `fill_packet`(헤더·시각·데이터를 바이트로 복사) → `send_echo`(전송) → 응답 버퍼 초기화 → `recv_echo`(대기·수신·timeout) → `handle_response`(관련 응답 확인·RTT/오류 출력).
4. 한 홉의 Probe 완료 후 `ttl++`.
5. `update_echopkt`가 **다음 패킷 헤더 구조체**에 TTL 반영.
6. 마지막 응답 버퍼의 출발지 IP로 중단 판단(이것은 원본의 설계이며 안전한 종료 규칙은 아님).
7. 바깥 `while` 조건 재평가.

**반드시 이해할 3층 상태:** `mgr->ttl`(관리 값) ↔ `msg.iphdr.ip_ttl`(헤더 구조체) ↔ `pkt`(송신 버퍼). `mgr->ttl++`만 수행하면 구조체/버퍼가 자동으로 갱신되지 않는다. `update_echopkt` 다음 `fill_packet`을 거쳐야 새로운 TTL이 실제 바이트에 나타난다.

### D. 이미 한 Rust 기초와 Java 비교

| 개념 | Rust | Java와 비교 | 이 차시에서 하는 일 |
|---|---|---|---|
| 상수 | `const START_TTL: u8 = 1` | `static final`과 일부 유사 | 설정 기본 기준값 |
| 불변 변수 | `let domain` | `final` 지역 변수와 일부 유사 | 변경되지 않는 목적지 |
| 가변 변수 | `let mut ttl` | 일반 지역 변수와 비슷 | 루프 내 상태 갱신 |
| 함수 | `fn print_probe(ttl: u8, probe: u8)` | 메서드/함수, 타입 명시 차이 | 출력 로직 분리 |
| 매크로 | `println!` | `System.out.println` 메서드와 구현 모델 다름 | 문자열 포맷 출력 |
| 포함 범위 | `1..=3` | Java `for (i=1; i<=3; i++)` 유사 | TTL·Probe 반복 |

**제출 확인:** 불필요한 `mut`을 제거한 학습자 코드 제출 완료. `cargo run`의 TTL 1~3 각 3회 출력 확인. Clippy의 `Finished dev profile` 로그 확인. `cargo fmt --check` Exit Code는 아직 미확인.

### E. 1차시 보충 학습 순서(정답은 먼저 주지 않음)

1. 상태 그림 없이 'TTL 관리 변수만 2로 바꾸면 실제 패킷은 어떤 값을 갖나?'에 답해본다.
2. `update_echopkt`와 `fill_packet` 역할을 각각 1문장씩 설명한다.
3. 라우터가 TTL=1 패킷을 전달하려 하면 어떤 일이 일어나는지 Type/Code를 정확히 말한다.
4. `*` 1개를 보고 **말할 수 있는 사실**과 **알 수 없는 사실**을 분리한다.
5. 맨 처음 틀렸던 질문을 그대로 다시 내기보다 다른 값(TTL=4, 프로브 수=2)을 제시해 독립적으로 추론하게 한다.

## 2차시 — Rust 개발 환경과 기초 문법

### A. 먼저 해야 할 단 한 가지 실습(현재 재개 위치)

```bash
rustup show active-toolchain
```

출력을 제출하고 **`rustc` = 컴파일러, `rustup` = 툴체인 설치/선택 관리자, `cargo` = 패키지·빌드·테스트 도구**를 Java JDK/Gradle/SDKMAN과 비교하여 2~3문장으로 설명한다. 아직 답을 받지 않았으므로 **성공·완료 표시 금지**.

### B. Cargo 구조 및 도구(개념 → 실제 파일)

- `Cargo.toml`의 `[package]`, `name`, `version`, `edition`, `[dependencies]` 각각 설명. 로컬 파일로 실제 Edition 확인.
- `Cargo.lock`: 의존성 해석 결과. Binary crate는 커밋. `target/`는 빌드 결과이므로 .gitignore.
- `src/main.rs`: Binary crate 진입. `src/lib.rs`: library crate. 패키지는 복수 Target을 가질 수도 있음을 기본 수준에서 이해.
- `cargo check`(코드 유효성 빠른 검사), `build`(바이너리), `run`(빌드+실행), `test`, `fmt`(형식), `clippy`(lint).
- `rustc --version`이 1.100.0이라고 Edition=2024가 자동 확정되는 것은 아님. Edition은 매니페스트에서 결정.

**개별 실습 순서:** 도구 설명 → 매니페스트 읽고 예상하기 → `cargo check` → `cargo build`/실행 파일 위치 관찰 → `cargo run` → `cargo test` → `cargo fmt --check; echo $?` → `cargo clippy -- -D warnings`. 한 명령씩 실행하고 출력/Exit Code 확인 후 다음. 이미 제출된 출력은 반복을 강제하지 않되 미확인은 채운다.

### C. 핵심 문법(`main.rs`에서 직접 확인)

| 학습 대상 | 이해할 경계와 Java 비교 | traceroute 시뮬레이터 응용 |
|---|---|---|
| `let`, `let mut`, `const` | 바인딩/변경/컴파일러 경고; Java `final`은 완전 동등하지 않음 | 목적지·현재 TTL·상수 |
| `u8/u16/u32/usize/bool` | 고정 폭 정수와 인덱스 크기, Java `byte`는 signed | TTL(u8), UDP port(u16), 길이(usize) |
| `String` / `&str` | 소유한 UTF-8 문자열 vs 뷰, Java String과 다름 | 목적지 표시/함수 인자 |
| `fn`, 인자와 반환 타입 | 반환값은 마지막 표현식 또는 `return`, Java 문장·표현식 차이 | TTL 범위 검사 함수 |
| `if/else` | 조건이 반드시 `bool`, `if`도 값이 되는 표현식 | TTL 오류, 정상/오류 상태 |
| `for`, `..`, `..=` | 배타/포함 범위, Java 전통 `for`와 형태 다름 | 홉별 Probe 순회 |
| `while` | 조건 확인 반복, 가변 카운터와 종료 조건 확인 | C `ping_loop`에 대응 |
| `loop`/`break` | 무조건 반복 → 명시 종료; 무한 루프 위험 | 종료 상태를 구현하는 연습 |

### D. 기존 코드 확장 — **한 번에 하나씩** 직접 구현

아래는 **연속해서 줄 과제의 명세**이지 지금 한 번에 작성할 코드가 아니다.

1. 이미 수행한 `domain`의 불필요한 `mut` 제거를 유지.
2. 도메인 출력만 별도 함수로 분리. 먼저 함수 인자 타입을 스스로 정함.
3. 유효한 TTL 범위 여부를 반환하는 함수를 구현하고 `if`로 경고 메시지를 분기.
4. `for` 기반 TTL 반복을 `while`로 변경하고 예상 출력 비교.
5. `loop`/`break`로 종료 조건만 재현, 비정상 입력에서 무한 반복 방지.
6. 홉당 Probe 3회를 유지하고 `ttl=MAX_TTL`에서 정확히 종료.
7. 오류 상황을 가정해 `max_ttl < start_ttl` 또는 0 입력을 구분하고 메시지 출력.
8. 기존 함수 구조·타입 선택·가변성·오류 처리 방식의 이유를 자신의 말로 설명.
9. 최종 통합 코드에서 `cargo` 검사를 실행하여 **실제 결과** 제출.

힌트 정책: 요구/테스트만 → 왜 틀렸는지 질문 → 의사코드 → 최소 문법 예시 → 제한적 해설. **완성 프로그램 제공 금지**.

### E. 원본과 시뮬레이터 비교 실습

- 시뮬레이터는 내부 `println!`만 수행하고 실제 패킷은 보내지 않는다.
- C `ping_loop`와 Rust `for`/`while`에서 반복 기준과 카운터 초기화 위치를 대응시킨다.
- C 원본의 Probe 내부에는 버퍼 생성·send·recv·handle이 있지만 Rust 학습 시뮬레이터는 출력 함수뿐이라는 차이를 설명한다.
- C의 `t_mgr` 상태 변경과 Rust 지역 변수 변경, `const`와 `#define`의 타입 차이 등은 **동일하다고 무작정 주장하지 않는다**.

## 1주차 패킷 관찰(Phase 6)

[macOS 실험 절차](../03-labs.md)에 따라 승인된 대상에만 `traceroute -n -m 5 -q 1 -w 1 <승인된_IPV4>`. 먼저 `man traceroute`로 옵션 확인. `route -n get <IP>`와 실제 인터페이스를 확인하고 `tcpdump`/Wireshark로 가능한 범위 내 관찰.

**제출할 표:** TTL/응답자 IP/RTT/`*`/ICMP Type/Code/송신 UDP 포트/관찰 또는 미관찰 이유. 출력의 TTL 1,2,3이 **패킷 헤더에 나타나는지**를 캡처로 확인. 미관찰 시 통제된 VM/예제 패킷으로 동일한 필드 추적을 하고 이를 대체 증거로 표기.
