# W10 — ICMP Echo와 공통 추적 엔진 (마일스톤 M3)

**선수조건:** W09 UDP traceroute 검증 완료. ICMP Echo 모드는 UDP의 종료 조건을 단순히 바꾸는 것이 아니라 **송신 패킷 구성과 응답 매칭 규칙 자체가 다르다**는 사실을 배운다.

**주간 산출물:** 사용자 모드 선택(`-I`), 유효한 Echo Request/Reply, 공유 Trace Engine/서로 다른 프로토콜 전략, 통합 테스트·pcap. **M3: 두 모드 모두 의미적으로 올바른 경로 추적**.

## 1차시 — ICMP Echo 패킷과 응답

### 네트워크 원리

- ICMP Echo Request: **Type 8 Code 0**. Echo Reply: **Type 0 Code 0**(IPv4).
- Echo Identifier/Sequence Number, Checksum, Payload의 의미. UDP Source/Destination Port 대신 ID/Sequence로 Probe를 식별한다.
- TTL 만료는 ICMP Echo 요청에서도 **Time Exceeded 11/0**으로 나타날 수 있다. 관련 Echo 요청이 **오류 메시지에 인용되므로**, 일반 Echo Reply와 **다른 파싱 경로** 필요.
- 일부 호스트/방화벽은 Echo Reply를 제한하므로 무응답을 목적지 고장으로 단정하지 않는다.

### Rust 개념

- `enum ProbeProtocol`: `Udp` 또는 `IcmpEcho`. 사용하지 않는 필드를 무조건 설정 구조체에 끼워 넣는 설계의 단점.
- Java 인터페이스·전략 패턴과 Rust `trait`/`enum + match`를 비교. 두 접근의 복잡도와 테스트 쉬움에 따라 결정.
- 프로토콜별 송신 형태와 공통 `HopResult`/`ProbeOutcome` 타입 분리.

### C 원본 독해

[`traceroute.c`](https://github.com/Dauie/traceroute/blob/master/src/traceroute.c) `update_echopkt`에서 `flags.icmp`이면 `ft_seticmp_hdr`, 아니면 `ft_setudp_hdr`. `fill_packet`도 모드에 따라 헤더 복사 대상이 달라진다. [`traceroute.h`](https://github.com/Dauie/traceroute/blob/master/incl/traceroute.h)의 `-I`, PID/TTL/포트와 C 비트 플래그 역할을 확인.

### 단계별 실습

1. ICMP Echo Request 헤더에 필요한 필드를 종이에 그린다.
2. Identifier/Sequence를 **Probe마다 추적 가능**하도록 생성 규칙 설계.
3. ICMP checksum 계산을 W04에서 익힌 바이트·checksum 원리와 연결.
4. 요청 송신과 Echo Reply 파싱을 분리하여 모의 패킷으로 먼저 테스트.
5. Echo Reply는 **Identifier/Sequence/주소**가 내 요청과 맞을 때만 완료 처리.
6. ICMP Time Exceeded 안에 인용된 Echo Request도 안전하게 매칭하도록 W07 전략 확장.
7. 허가된 VM에서 소량의 Echo Probe로 송신/수신 및 응답 비교 캡처.

### 테스트

| 수신 | 예상 |
|---|---|
| 같은 ID/Sequence를 가진 Echo Reply 0/0 | 해당 Probe 도달 |
| ID 또는 Sequence가 다른 Echo Reply | 무관 |
| Echo Request에 대한 ICMP Time Exceeded 11/0 | 홉 기록, 계속 |
| 잘린 Echo/quoted packet | 오류/무시, panic 없음 |
| Echo Reply 차단/timeout | `*`/timeout, 성공 단정 금지 |

## 2차시 — 공통 Trace Engine과 CLI 옵션 통합

### 설계 문제

- `TraceEngine`이 공유해야 하는 것은 무엇인가? TTL/Probe 순회, deadline, 시간 측정, 출력 형식, 실패/완료 상태.
- 모드별로 달라야 하는 것은 무엇인가? Probe 구성, ICMP 응답 파싱/매칭, 목적지 도달 조건, 권한 요구.
- `trait` vs `enum`을 선택한 이유와 Java 다형성 비교. **추상화 자체가 목표가 아니라 테스트 가능한 분리**가 목표.
- `-I` 모드를 켤 때 CLI → 설정 → 송신기 → 매처 → 결과 출력까지 연결.

### C 원본 전체 흐름 비교

`main.c`의 `parse_args` `-I` 설정 → `create_sock` 모드별 송신 socket → `traceroute.c` `initialize_echopacket` → `update_echopkt`/`fill_packet` → `send_echo`/`recv_echo`/`handle_response`. C의 전역 상태·플래그를 Rust의 명확한 타입으로 표현하되 C와 byte-for-byte 동일할 필요는 없음.

### 직접 구현 과제

1. 두 모드의 차이/공통점 표를 먼저 작성.
2. 기존 UDP 코드의 불필요한 복제를 찾고 공유할 수 있는 구조만 추출.
3. 모드에 따라 Probe Builder, Matcher, Terminal Detector를 선택.
4. 정상/timeout/무관 응답에 동일한 표시 규칙을 적용하는 통합 테스트.
5. 잘못된 모드 옵션/권한 부족 시 사용자 친화적 메시지.
6. UDP 모드에서 Echo Reply를 목적지 도달로 오인하지 않는 테스트 및 반대 방향의 오류 방지.
7. 허가된 환경에서 **UDP 및 ICMP 두 모드의 캡처**를 비교하고 결과 차이 설명.

## M3 최종 게이트

- [ ] UDP traceroute에서 매칭된 ICMP 3/3 종료.
- [ ] ICMP Echo traceroute에서 매칭된 Echo Reply 0/0 종료.
- [ ] 11/0은 두 모드에서 홉 정보로 해석, 무관 응답 거부.
- [ ] timeout/RTT/Probe 여러 개, 최소 5개 비정상 시나리오가 테스트됨.
- [ ] `cargo test/fmt/clippy` 증거와 승인된 패킷 관찰.
- [ ] CLI `-I`/기본 UDP의 입력/오류 처리가 구별됨.
