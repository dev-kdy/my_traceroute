# W12 — 격리된 다중 홉 실험·리팩터링·최종 독립 구현

**선수조건:** W11 경계·회귀 테스트 통과. 마지막 목표는 **개발자가 자신의 소스에서 증명 가능한 동작을 재현하고 네트워크 관측의 한계까지 설명하는 것**이다.

**최종 결과물:** 독립 실행 CLI, 자체 설계 문서, 재현 가능 실험, pcap/테스트 보고서, 사용자 매뉴얼, 12주 학습 회고, 추후 개선 백로그.

## 1차시 — Linux 격리 다중 홉에서 원리 확인

### 환경과 보안

- Ubuntu VM/실습용 격리 환경에서 `ip netns`, `veth`, `ip route`, IP forwarding의 역할을 먼저 이해한다.
- **호스트 네트워크의 기본 라우팅/포워딩을 함부로 변경하지 않는다.** 가능하면 VM 내부 namespace에만 적용. 실습 전 복구 순서 작성.
- 초기 그래프: 송신 namespace → 라우터 namespace A → 라우터 namespace B → 목적지 namespace. 실제 생성 명령과 인터페이스 주소는 학습자가 VM 상태 확인 후 설계하고 제출; 문서에는 무조건 실행하는 위험한 일괄 설정 스크립트를 제공하지 않는다.
- 각 라우팅 홉에서 TTL이 어떻게 감소하는지, 어느 네트워크 인터페이스에서 캡처해야 하는지 **패킷 전송 전 가설** 작성.

### 단계별 실습

1. 종이에 네트워크 토폴로지, 각 인터페이스·대역/next-hop·라우팅 테이블 설계.
2. `ip netns`/`veth` 개념과 라우터 IP forwarding을 공식 Linux 자료로 확인.
3. 네임스페이스별 연결/라우팅을 한 개씩 설정하고 `ip route`/`ping` 등으로 독립 검증(본인 VM에 한함).
4. TTL=1/2/3 Probe가 각각 어디서 폐기/응답될지 예상.
5. 송신/중간 라우터/목적지의 캡처 지점을 결정하고 ICMP Type/Code를 기록.
6. 자신의 UDP traceroute와 시스템 traceroute를 비교, 포트/식별자/timeout/최대 TTL 차이 기록.
7. 의도적인 ICMP 제한 또는 응답 지연을 **격리 환경에만** 넣고 `*`, retry/timeout 의미 확인.
8. 실험 환경을 안전하게 정리하고 네트워크 구성이 원래대로 복구되었는지 확인.

### 예상 관측과 실제 관측 분리

| Probe 상태 | 이론상 기대 | 실제 기록 필수 |
|---|---|---|
| TTL=1 | 첫 전달 라우터의 Time Exceeded 11/0 가능 | 송신 TTL, 라우터 IP, ICMP 프레임 |
| TTL=2 | 둘째 라우터의 Time Exceeded 11/0 가능 | TTL 감소와 quoted 원본 패킷 |
| 목적지에 도달한 UDP | 포트 미사용이면 3/3 가능 | 대상 포트·응답 매칭 후 종료 |
| ICMP Echo 목적지 | 일치하는 Echo Reply 0/0 가능 | ID/Sequence 검증 |
| ICMP 제한/방화벽 | `*`일 수 있음 | 제한 설정/증거, 단절로 단정 금지 |

실제 경로, hop 수, 응답 IP가 예측과 다르면 먼저 **네임스페이스 연결·라우팅 설정·캡처 위치·방화벽·권한·송신 포트**를 확인한다. pcap을 보고도 매칭이 불명확하면 통과시키지 않는다.

## 2차시 — 관찰의 한계와 유지보수 가능한 Rust CLI

### 네트워크의 한계

- **NAT:** 송신 IP/포트를 변환하므로 인용 정보 및 Probe 연결에 영향.
- **ECMP:** 다중 동등 경로에서 Probe의 5-tuple 등 필드에 따라 다른 경로가 선택될 수 있음.
- **비대칭 경로:** 요청과 ICMP 응답의 경로가 같지 않을 수 있음.
- **ICMP filtering/rate limiting:** 일부 장비가 보낼 수 있는 응답을 제한; `*`는 중간 장애 증거 아님.
- **MPLS·터널·로드밸런싱:** 일반 traceroute 결과만으로 모든 중간 장비/정확한 물리 경로를 확정 불가.
- **RTT:** 각 홉까지의 왕복 지연이고, 홉 간 링크의 단방향 지연을 직접 계산할 수 없음.

### Rust 설계 최종 리뷰

1. CLI/Config/Probe/PacketParser/Socket/ResponseMatcher/Timer/TraceEngine/Output 역할을 그림으로 나눈다.
2. 파서와 소켓이 결합되지 않아 외부 네트워크 없이 테스트되는지 확인.
3. 불필요한 `clone`/`mut`/`unsafe`, 정수 overflow, unchecked indexing, 추상화 남용을 검토.
4. `unsafe`·FFI를 쓰는 경우 경계와 불변 조건을 문서화; 가능하다면 안전한 API를 먼저 선택.
5. 디버그/릴리스 빌드, 사용법/에러 메시지, 필요한 Linux 권한, OS 지원 범위 문서화.
6. 의존성 `clap`/`socket2` 버전 고정과 `Cargo.lock` 관리, 외부 C 소스 재배포 라이선스 주의.
7. CPU/메모리 최적화보다 **정확성과 재현 가능성** 우선. 비정상 네트워크 조건에서도 반복 가능한 결과를 만들 것.

| 영역 | 배점 | 시연/설명 |

| 실측·테스트 재현 | 20 | 단위 테스트·VM 캡처·명령·Exit Code·환경 정보 |
| C 원본 설명 | 10 | 확인된 C 설계 사실과 Rust 개선/검증 가설 구분 |
| 새로운 시나리오 대응 | 5 | 낯선 오류/필터링/경로 변경의 원인 분석 |

### 최종 시연 순서(답안은 학습자 본인이 준비)

1. 클린 빌드 → `cargo fmt --check` → `cargo clippy -- -D warnings` → `cargo test` → CLI `--help`.
2. 정상 UDP 경로 추적 및 ICMP Echo 모드 비교.
3. TTL 최대값, Probe 수, timeout 설정 변화에 따른 결과 관찰.
4. 의도된 잘못된 CLI 입력/권한 부족, 잘린 패킷·무관 응답·late reply 테스트.
5. 실제 pcap에서 송신 Probe와 수신 ICMP를 **필드 값으로** 매칭하는 시연.
6. C `ping_loop` 호출 구조, `check_packet` 고정 오프셋 가정, 원본 IP 비교 종료와 내 설계의 차이를 설명.
7. 결과가 실행마다 달라지는 원인을 NAT/ECMP/비대칭/ICMP 제한과 연결.
8. 아무 힌트 없이 작은 요구 변경(예: max TTL/Probe 수 정책 또는 timeout 방식)을 설계하고 테스트 추가.
