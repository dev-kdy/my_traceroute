# W08 — RTT·Timeout·Deadline과 시계

**선수조건:** W07에서 Probe별 응답 매칭이 정확하다. W08은 **맞는 응답에 대해서만** 시간을 측정하고, 시간이 지난 응답을 구별한다.

**주간 산출물:** `Instant`/`Duration` 기반 Probe 시간 측정 모듈, 명시적인 deadline 상태, 시간 의존성을 분리한 결정적 테스트.

## 1차시 — Rust Instant와 Duration

### 개념

- RTT(Round-Trip Time): 한 Probe의 송신 시각부터 **그 Probe와 매칭된 응답**의 수신 시각까지의 경과 시간. 편도/홉 간 실제 전송 지연과 다름.
- `std::time::Instant`: 경과 시간 측정에 적합한 단조 시계 개념. `SystemTime`은 벽시계 변경의 영향을 받는다.
- `Duration`: 시간 간격 타입, `as_secs_f64` 등으로 밀리초 표시할 때 단위 환산 유의.
- 오버헤드와 정확도: OS scheduling, 큐 대기, ICMP 라우터 처리, 응답 경로에 따라 실제 RTT가 달라진다.
- Java `System.nanoTime()`/`Duration`과 비교하되 두 언어/OS가 정확히 같은 clock 구현이라고 단정하지 않는다.

### C 원본 전체 분석

[`traceroute.c`](https://github.com/Dauie/traceroute/blob/master/src/traceroute.c) `fill_packet`의 `gettimeofday(&msg->sent)`와 [`send_recv_echo.c`](https://github.com/Dauie/traceroute/blob/master/src/send_recv_echo.c) `recv_echo`의 `gettimeofday(&msg->recvd)`, [`handle_response.c`](https://github.com/Dauie/traceroute/blob/master/src/handle_response.c)의 `ft_timediff_ms` 호출 순서를 그린다. 시스템 시계 조정이 RTT 값에 영향을 줄 위험을 **가설**로 적고 Rust에서는 단조 경과시간 API를 사용한다.

### 스스로 구현할 작은 실습

1. `Probe` 안에 송신 시간과 식별자 중 어떤 필드를 넣을지 설계.
2. 송신 직전/직후 시각 중 어떤 기준으로 측정할지 선택하고 오차 논의.
3. 맞는 응답을 확인한 뒤에만 RTT 계산/출력.
4. 단위가 ms인 문자열로 변환하며 초·밀리초 환산 테스트.
5. clock을 직접 호출하는 함수를 좁히고, 함수 밖에서 시간을 주입해 모의 테스트 가능하게 설계.
6. clock 값이 기대 범위와 다른 상황과 시스템 시간 변경 차이를 설명.

## 2차시 — Deadline/Timeout/late reply

### 개념

- Timeout: 어떤 작업의 **대기 기한**이 지났다는 상태. 패킷 손실이나 목적지 장애를 직접 증명하지 않음.
- Deadline: 기준 시작 시각과 허용 대기 시간을 조합한 시점. 무관한 ICMP가 올 때마다 대기 시간이 무한히 연장되면 안 된다.
- 한 Probe가 두 번 응답하거나 이미 종료된 Probe의 답이 늦게 오면 중복 RTT/성공 종료를 허용하지 않는다.
- 복수 Probe를 순차/동시 전송할 때 각 Probe의 timeout이 어떻게 분리되는지 상태도로 표현.

### C 독해

[`send_recv_echo.c`](https://github.com/Dauie/traceroute/blob/master/src/send_recv_echo.c) `recv_echo`의 `DEF_WAIT_TIME`, `select`, `ret<=0` 분기와 [`traceroute.c`](https://github.com/Dauie/traceroute/blob/master/src/traceroute.c)의 결과 처리 반환값 무시를 비교. 수신이 실패해도 버퍼/시각이 안전한가? 테스트가 필요한 가설로 남긴다.

### 직접 구현 흐름

1. `Pending / Matched / TimedOut / Failed` 상태 모델 정의.
2. 시작 시각과 deadline을 비교하는 **순수한 판단 함수**를 만들어 테스트.
3. 예상 대기시간 100ms인 가상의 Probe에서 30ms(일치), 70ms(무관), 99ms(일치), 101ms(지연)를 가정해 결과 예측.
4. deadline 지난 결과는 `*`로 처리하되 늦은 응답을 다음 Probe에 귀속하지 않음.
5. 일치하지 않은 수신이 계속 와도 deadline을 처음부터 리셋하지 않도록 구현.
6. 정상·타임아웃·무관 응답·지연·중복·clock 경계 단위 테스트 추가.

### 테이블 기반 테스트 조건

| 시나리오 | 기대되는 시스템 상태 |
|---|---|
| 유효한 응답이 deadline 이전 | RTT 계산, 완료 |
| deadline에 도달했는데 무응답 | Timeout, `*` 표시 |
| 무관한 ICMP만 도착 | Probe에 매칭하지 않음, 기존 deadline 유지 |
| 과거 Probe 응답이 나중에 도착 | 현재 Probe에 합치지 않음 |
| 동일 Probe 응답 중복 | RTT 한 번만 기록 |
| 소켓 읽기 오류 | `Timeout`과 다른 오류 처리 |
