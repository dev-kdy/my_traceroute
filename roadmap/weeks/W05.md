# W05 — UDP와 커널 네트워크 스택

**선수조건:** W04의 IPv4/UDP 파서와 안전한 slice 처리. 이번 주부터 **실제 송신**을 시작하므로 본인/승인 네트워크에서만 실험. 목적지 응답 **수신 구현과 도달 판정은 아직 범위 밖**.

**주간 결과:** `std::net::UdpSocket` 기반 TTL 조정 UDP 발신기, 소량 송신 캡처, 라우팅/ARP 관측 노트, 오류 처리 로그.

## 1차시 — 소켓과 Rust I/O 오류

### 새로운 개념

- Socket: OS가 제공하는 네트워크 I/O endpoint; socket descriptor와 Rust `UdpSocket` 객체의 차이.
- `bind`/`send_to`/`set_ttl`/`local_addr`와 동작 범위. 단순 UDP socket을 쓰면 일반적으로 UDP/IP 헤더의 대부분은 **커널이 구성**한다. 원본 C의 raw socket 방식과 다름.
- `std::io::Result`/`?` 및 `Drop`: 네트워크 작업 실패와 리소스 해제, Java `DatagramSocket`/`try-with-resources`와 비교.
- 목적지 `SocketAddr`의 주소/포트와 로컬 주소/포트 구분. DNS 이름은 W03에서 IP로 해석하고 송신 전 검증.
- `set_ttl`을 어디서 호출해야 **그 Probe의** 송신 TTL에 반영되는가? 다음 TTL용 상태와 기존 송신 버퍼는 별개.

### C 원본 전체 함수 독해

[`main.c`](https://github.com/Dauie/traceroute/blob/master/src/main.c)의 `create_sock()`: 송신 raw/수신 ICMP raw socket 생성, `IP_HDRINCL`, UDP 모드 bind. [`send_recv_echo.c`](https://github.com/Dauie/traceroute/blob/master/src/send_recv_echo.c)의 `send_echo()`: `sendto` 반환값과 실패시 즉시 종료하는 흐름. **일반 UDP socket 모델과 직접 패킷 헤더 구성 모델이 다른 이유**를 표로 비교.

### 직접 실습(작은 순서)

1. **송신 계약부터 작성:** 대상 IPv4/UDP port, TTL 입력, 송신 성공/실패 결과, 외부 패킷 캡처 계획.
2. 승인된 한 IP에 최소한의 데이터와 TTL=1인 UDP 송신을 수행하는 함수 설계.
3. 타입·주소 파싱·소켓 오류를 `Result`로 반환. 임의 `unwrap`/과도한 관리자 권한 금지.
4. TTL=2와 3으로 바꾸되, **실측이 동일한가**를 캡처 전에 예측.
5. 실제 송신 `stdout`만 보고 성공 선언하지 말고 인터페이스 `tcpdump`/Wireshark로 IPv4 TTL·프로토콜 17·UDP Port 확인.
6. 예상하지 못한 `No route to host`/`Permission denied`/DNS 실패를 오류 종류별로 기록.

**중요한 질문:** Java 애플리케이션이 DatagramPacket을 send 했을 때도, 대부분의 IP/Ethernet 헤더를 Java 코드가 직접 만드는가?

## 2차시 — 라우팅·서브넷·ARP·다음 홉

### 네트워크 개념

- 주소: Source/Destination IPv4, subnet/prefix, loopback/동일 LAN/다른 네트워크 구분.
- Routing Table/Default Gateway: 목적지 IP를 기준으로 네트워크 인터페이스와 next-hop을 선택.
- Ethernet: 최종 IP 목적지는 원격 서버여도 L2 목적지 MAC은 **다음 홉 라우터**일 수 있음. ARP는 IPv4에서 이웃 IP↔MAC 해석, 원격 목적지 MAC을 항상 찾는 것은 아님.
- TTL은 IP 계층의 필드이며 스위치의 일반적인 L2 전달과 라우터의 L3 전달을 구별.
- NAT, ICMP 제한, 오프로드, VM NAT 설정이 관찰에 미치는 영향.

### 원본 연관 파일 읽기

[`set_addr_iface.c`](https://github.com/Dauie/traceroute/blob/master/src/set_addr_iface.c) `set_addr_iface`/`set_addr` 함수 전체에서 source address, 인터페이스, `setsockopt` 호출 순서를 살핀다. [`main.c`](https://github.com/Dauie/traceroute/blob/master/src/main.c)에서는 `parse_args`가 `create_sock`보다 **앞**임을 확인하고 위험 가설을 기록하되 재현 없는 확정 버그 발표 금지.

### macOS/Ubuntu 실험 분기

- macOS: `route -n get <승인된_IP>`, `ifconfig`, 실제 인터페이스 선택, `sudo tcpdump -ni <iface> -vv 'udp or icmp'`.
- Ubuntu: `ip route get <승인된_IP>`, `ip addr`, `ip neigh`, `sudo tcpdump -ni <iface> ...`.
- **실제 허가 대상**만 사용. 기기와 네트워크가 변동하면 실행 전에 다시 확인한다.

**종이 실습:** 로컬 IP와 다른 서브넷의 허가 대상 IP가 주어졌을 때 IP Destination, next-hop IP, Ethernet Destination MAC의 역할을 각각 쓰고, ARP 요청 대상이 누구인지 예측.
